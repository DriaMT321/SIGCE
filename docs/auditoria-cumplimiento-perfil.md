## Límites de cumplimiento

- La integración con el portal oficial SIE permanece deshabilitada por configuración. El anexo G del perfil limita esas pruebas a un entorno controlado y datos institucionales anonimizados; no se ejecutó acceso real ni se usaron credenciales reales.
- RF-47 y RF-48 (navegación autenticada y transferencia al portal oficial por el worker) siguen pendientes: la sección 3.8.1 del perfil indica que el SIE oficial no estaba habilitado y condiciona esas pruebas a disponibilidad y autorización institucional. El worker implementa y prueba una simulación local; eso no demuestra una transferencia real. No se añadieron selectores de transferencia al worker ni una secuencia de envío especulativa.
- Las migraciones nuevas están preparadas, validadas y generaron el cliente Prisma, pero **no se aplicaron a ninguna base de datos**. Antes de desplegar, se debe respaldar la base y ejecutar el procedimiento de [operaciones de base de datos](operaciones-base-datos.md).
- La revisión contrasta el código con RF-01–RF-56, RNF-01–RNF-20, RN-01–RN-24 y CA-01–CA-17. No reemplaza la aceptación institucional ni la validación de extremo a extremo en el despliegue. Quedan pendientes de evidencia de operación real: TLS en el proxy de producción, configuración de `TRUSTED_PROXY_IPS` con IPs exactas y normalización de `X-Forwarded-For` en el proxy, una prueba de carga con umbrales aprobados, un ensayo de restauración sobre una base desechable y la autorización/validación del SIE oficial. La compilación APK tampoco se verificó: el equipo no tiene Java ni Android SDK; sí se comprobaron las pruebas y la compilación Flutter web. Las comprobaciones automatizadas de accesibilidad cubren las pantallas móviles ejercitadas, no una auditoría completa de WCAG 2.2 en todas las pantallas ni con tecnologías de asistencia.
- El repositorio contiene un respaldo SQL histórico. Se debe decidir su tratamiento y distribución con quien custodia los datos; esta auditoría no modificó ese respaldo.
- Los valores iniciales de pausa por discrepancias (20%) y plazo de revisión (72 horas) son configurables en el worker; Dirección debe confirmarlos antes de un despliegue institucional.
- El repositorio conserva respaldos SQL históricos en `database/`; su contenido no se inspeccionó ni se modificó. La persona responsable de los datos debe decidir si pueden distribuirse dentro del repositorio.
- Los secretos JWT ilustrativos del `.env.example` se rechazan en producción; la contraseña PostgreSQL se identifica como valor de desarrollo local.

## Clean Architecture y DDD

La API y el worker **aplican Clean Architecture**: presentación HTTP, aplicación, dominio e infraestructura tienen dependencias hacia adentro; los casos de uso consumen puertos; los adaptadores NestJS/Prisma/BullMQ/Puppeteer y las operaciones de archivos están fuera del dominio y la aplicación. NestJS compone los casos de uso en el borde. Las validaciones HTTP viven en presentación. La aplicación móvil también separa presentación, dominio (entidades, políticas y casos de uso) y datos; las pantallas no acceden directamente a adaptadores HTTP o de caché. La web sigue organizada por funcionalidades; sus límites de capa ahora se verifican con cero importaciones directas desde presentación a los adaptadores compartidos y cero accesos directos a socket. La barrera escanea fuentes TypeScript, JavaScript y Dart, excluye pruebas de esos lenguajes, reconoce imports ESM y CommonJS, incluida la forma `module.require`, resuelve imports relativos y alias según las configuraciones TypeScript reales, reconoce los URI Dart `package:mobile_app/`, verifica que los cruces entre contextos de API terminen en puertos de aplicación resueltos, detecta ciclos entre módulos de API, comprueba el mapping web contra `apps/web/tsconfig.json`, reconoce subpaths de paquetes y módulos nativos de Node, rechaza loaders dinámicos o alias no verificables en capas restringidas, el acceso directo a I/O del navegador (también mediante aliases, CacheStorage, WebRTC/WebTransport, temporizadores con código, `eval`, `Function` o acceso dinámico a `constructor`) en dominio/aplicación web y paquetes externos no permitidos en dominio/presentación móvil, verifica que los paquetes de dominio no dependan de frameworks o persistencia, detecta imports a barrels y fuentes web sin capa, inspecciona los widgets y temas móviles y trata proveedores/router como composición, y rechaza enlaces simbólicos en las rutas fuente. Incluida en `pnpm test`, comprueba además las reglas de capas y los cruces entre contextos que no usan puertos publicados.

El backend **aplica DDD**: sus módulos forman contextos delimitados, sus contratos hacen explícitas las colaboraciones y el dominio modela invariantes de matrícula, calificación, corrección, asistencia, reglas de alertas, horarios e integración SIE. `Calificacion` es una raíz de agregado; la matrícula coordina sus invariantes mediante `PoliticaInscripcion`, consultada dentro de la transacción. Las reglas de asistencia y alertas son políticas de dominio independientes de NestJS. El Shared Kernel `@academic/academic-domain` tiene ownership documentado entre currículo y organización académica y conserva las reglas educativas comunes. El caso de uso de generación de horarios coordina el modelo puro con puertos de persistencia. Para evitar perder reevaluaciones si se cae la API, cada cambio de asistencia y calificación, incluida la aprobación de una corrección, crea una tarea durable en PostgreSQL junto con el dato y su auditoría; el procesador reclama, reintenta y completa las tareas. Los modelos de consulta que no contienen comportamiento permanecen simples; DDD no requiere que cada registro relacional sea un agregado.

La arquitectura de dependencias se verifica en API, worker, cliente móvil y web. En web, el test confirma cero accesos directos de presentación a adaptadores HTTP, autenticación y socket. DDD se afirma para el dominio del backend, donde están modelados los contextos e invariantes descritos. No acredita la integración real con el SIE, el despliegue de producción, la aceptación institucional ni el conteo de tablas del perfil. Esos límites tienen evidencia y restricciones propias descritas en esta auditoría. El detalle de contextos, puertos y reglas se encuentra en la [guía de arquitectura Clean Architecture y DDD](arquitectura-clean-ddd.md).
