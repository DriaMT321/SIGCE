# Arquitectura Clean Architecture y DDD en SIGCE

## Alcance

La arquitectura de servidor comprende la API modular (`apps/api`). Sus módulos separan presentación, aplicación, dominio y adaptadores de infraestructura. NestJS y Prisma son detalles externos a los casos de uso y al dominio. La web, el móvil y la extensión de Chrome son clientes de la API, no contextos de dominio independientes. El móvil ya separa presentación, dominio y datos. La web conserva organización por funcionalidades y su regla de dependencias internas se verifica en todas las capas.

SIGCE es un monolito modular: sus contextos comparten el proceso de la API y el esquema PostgreSQL. DDD no exige una base distinta por contexto. Cada módulo mantiene la propiedad de sus operaciones y repositorios; la comunicación síncrona de la aplicación entre módulos se expresa mediante puertos publicados en `application/ports`. Como el esquema es compartido, algunos adaptadores Prisma también consultan relaciones de módulos vecinos para construir proyecciones; eso no expone Prisma a los casos de uso, aunque significa que la propiedad de tablas no está aislada por permisos de base de datos.

## Regla de dependencias

En cada módulo de API, los archivos de producción se organizan bajo `presentation`, `application`, `domain` o `infrastructure`; el archivo `*.module.ts` compone dependencias en el borde de NestJS. La dirección del código es hacia adentro:

```text
presentation ──► application ──► domain
infrastructure ──► application/domain
*.module.ts ──► todas las capas para componer implementaciones
```

- `presentation` contiene controladores y DTOs HTTP con `class-validator`.
- `application` contiene casos de uso, comandos y puertos; no importa NestJS, Prisma, validadores HTTP, Redis ni APIs de archivos.
- `domain` contiene políticas, entidades, agregados y objetos de valor; no depende de infraestructura ni de frameworks.
- `infrastructure` implementa los puertos declarados en `application/ports` con Prisma, NestJS, Redis y archivos.
- `proveedorAplicacion` construye los servicios de aplicación en el límite de composición; el filtro HTTP traduce sus errores a respuestas HTTP.
- En web, cada funcionalidad puede alojar `presentation`, `application`, `domain` e `infrastructure` sin abandonar su organización por funcionalidad. La dirección verificada es presentación hacia aplicación/dominio e infraestructura hacia puertos internos; el directorio `app/composition` conecta ambas capas externas. El dominio y la aplicación no deben importar React, React Query, Axios, socket.io ni los clientes HTTP compartidos.

Las pruebas `scripts/limitesarquitectura.*.test.ts` comprueban estas dependencias, la ubicación de los controladores y de las validaciones HTTP, los cruces entre contextos de la API, la independencia móvil y las capas web en todo `apps/web/src`. Exigen cero importaciones directas desde presentación web hacia los adaptadores compartidos (`academic-api`, `api-client` y `auth.service`) y cero importaciones directas de socket. Ambos límites se cumplen actualmente y las pruebas impiden que vuelvan a crecer. La barrera escanea TypeScript, JavaScript y Dart; reconoce imports ESM, CommonJS y `module.require`; excluye pruebas TypeScript, JavaScript y Dart; resuelve rutas relativas, alias de TypeScript usando la configuración real de la API y el alias web `@/`, además de los URI Dart `package:mobile_app/`; determina si un cruce entre contextos de API termina realmente en un puerto de aplicación; comprueba el alias web frente a `apps/web/tsconfig.json`; normaliza sufijos como `.js`; reconoce subpaths de paquetes; rechaza loaders computados o alias no verificables en capas restringidas, incluido el acceso a `process.getBuiltinModule`; bloquea módulos nativos de Node, referencias a I/O del navegador (incluidos aliases, CacheStorage, WebRTC/WebTransport, temporizadores con código, `eval`, `Function` y acceso dinámico a `constructor`) en dominio/aplicación web, paquetes externos no permitidos en dominio/presentación móvil, dependencias externas en los paquetes de dominio y ciclos entre módulos de API; examina los widgets y temas de `mobile/lib/core` y deja proveedores y router como composición; clasifica dependencias web compartidas y las rutas de `mobile/lib/core`; detecta imports a barrels y rutas de feature sin clasificar; y rechaza enlaces simbólicos en las rutas fuente. Las pruebas se ejecutan como parte de `pnpm test`.

## Estructura móvil

La aplicación móvil materializa las tres capas descritas en el perfil. `features/*/presentation` contiene las pantallas; `features/*/domain` contiene entidades, políticas, contratos de repositorio y casos de uso; `features/*/data` implementa acceso HTTP, mapeo de respuestas y caché local. `core/providers` es el punto de composición que conecta los casos de uso con los adaptadores. La misma prueba de límites impide que las pantallas importen directamente adaptadores de datos.

El vocabulario central que aparece en los casos de uso y políticas incluye RUDE, gestión académica, período, curso, asignatura, matrícula, calificación, solicitud de corrección, asistencia, alerta, comunicado, sincronización SIE y grupo de discrepancias. Los puertos de auditoría y de evaluación de alertas hacen explícitas las colaboraciones entre contextos; los módulos consumidores no importan sus implementaciones de persistencia. `@academic/domain-kernel` concentra enums y valores compartidos del lenguaje del dominio; los dominios dependen de ese vocabulario y no de contratos de transporte. `@academic/shared-types` reexporta esos valores para compatibilidad de transporte y contiene los DTO y eventos públicos. `@academic/academic-domain` es un Shared Kernel explícito entre organización académica y currículo: mantiene la clasificación de niveles y las reglas horarias para que servidor y web apliquen el mismo modelo. Los cambios a los kernels deben conservar sus pruebas y coordinarse entre contextos consumidores.

## Mapa de relaciones entre contextos

Las relaciones describen colaboraciones de aplicación o lectura; los adaptadores conservan la traducción de formatos externos. El mapa evita interpretar cada importación como propiedad compartida de un modelo.

| Contexto que inicia                    | Contexto colaborador     | Relación en el código                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Autenticación y usuarios               | Auditoría                | Autenticación publica registros mediante el puerto `EscritorRegistroAuditoria`; el adaptador Prisma de usuarios guarda sus cambios y auditoría en una transacción. El módulo de usuarios consume además puertos de credenciales y revocación de sesiones de autenticación.                                                             |
| Estudiantes                            | Autenticación y usuarios | El servicio de activación consume el puerto de seguridad de credenciales; las entidades y tablas de ambos contextos siguen siendo propias.                                                                                                                                                                                             |
| Matrícula, cursos, docentes y familias | Auditoría                | Los casos de uso entregan el actor y la IP al puerto o adaptador correspondiente; las mutaciones auditadas se guardan con el registro de auditoría dentro de la misma transacción de persistencia.                                                                                                                                     |
| Calificaciones y asistencia            | Alertas                  | Los casos de uso consumen el puerto de evaluación temprana. El alta de asistencia publica `AttendanceRegisteredEvent` para respuesta rápida y crea una tarea de conciliación en PostgreSQL dentro de la misma transacción; un procesador con bloqueo recuperable y reintentos garantiza la entrega eventual aunque la API se reinicie. |
| Currículo y organización académica     | Shared Kernel académico  | Importan `@academic/academic-domain` para las reglas de nivel educativo y períodos pedagógicos; el paquete no depende de frameworks, persistencia ni transporte.                                                                                                                                                                       |
| API de preparación SIE                 | Extensión Chrome         | La API entrega solo notas cerradas y autorizadas; la extensión rellena los campos visibles en la sesión abierta por la responsable y registra un resumen de la operación. El guardado en el SIE queda a cargo de la responsable.                                                                     |
| Informes                               | Contextos académicos     | Construye proyecciones de lectura con el esquema compartido; no recibe autoridad para mutar modelos de esos contextos.                                                                                                                                                                                                                 |

## Modelo de dominio e invariantes

DDD se aplica con profundidad distinta según las reglas que tiene cada capacidad. Las invariantes se expresan en el dominio cuando cambian decisiones de negocio:

- `PoliticaInscripcion` comprueba que el estudiante esté activo, que el curso pertenezca a la gestión elegida, que esta siga abierta, que no exista otra matrícula y que haya capacidad; también protege la reactivación. Es una política de dominio consultada dentro de la transacción, no una raíz de agregado con estado propio.
- `ValorCalificacion` acepta solo valores finitos entre 0 y 100.
- El agregado `Calificacion` verifica sus referencias académicas al registrar una nota y aplica `ValorCalificacion` al crear o modificar antes de enviar los datos al repositorio.
- `SolicitudCorreccionCalificacion` valida la diferencia entre nota original y propuesta, el motivo y el respaldo; solo permite resolver una solicitud pendiente con una justificación suficiente.
- La política de asistencia exige motivo para marcar un registro como justificado y normaliza la fecha al día académico.
- `validarConfiguracionReglaAlerta` limita los umbrales de calificación e inasistencia y rechaza valores no finitos o fraccionarios donde la regla exige enteros.
- El caso de uso de generación semanal reúne la política pura del dominio con los puertos de carga y persistencia; el adaptador Prisma solo traduce datos y reemplaza el horario en una transacción. La política busca una asignación completa de sesiones antes de reportar un conflicto, y toma niveles y duraciones oficiales del Shared Kernel académico. Antes del reemplazo, el adaptador bloquea el curso y las asignaciones vigentes y compara la instantánea completa de asignaciones, nivel, turno, nombre y gestión usada por el caso de uso. Una migración añade un guard transaccional en PostgreSQL con bloqueo asesorado por docente y bloque, para impedir dobles asignaciones incluso ante generaciones concurrentes.

`Calificacion` es una raíz de agregado con identidad persistida, referencias académicas y el objeto de valor `ValorCalificacion`; una corrección mantiene su estado de decisión y rechaza una segunda transición. Los objetos de consulta y las tablas sin reglas propias pueden seguir siendo interfaces o estructuras simples. En DDD, la unidad agregada se define por invariantes y consistencia transaccional; no corresponde declarar cada fila de Prisma como agregado. Los repositorios adaptan esas estructuras al almacenamiento y no son el lugar de las reglas del dominio.

Los cambios de asistencia y calificaciones, incluidas cargas masivas y correcciones aprobadas, escriben una fila de `AlertEvaluationOutbox` para cada estudiante afectado dentro de la misma transacción que el dato y su auditoría. El bus en memoria conserva la respuesta rápida; el procesador consulta la bandeja cada 15 segundos, reclama filas con `FOR UPDATE SKIP LOCKED`, reintenta fallos con espera exponencial y elimina cada fila solo después de reevaluar al estudiante. Un bloqueo vencido permite recuperar tareas tras la caída de una instancia; la conciliación de alertas es idempotente y tolera una repetición si la instancia cae después de evaluar y antes de eliminar la tarea.

## Evidencia y límites de la afirmación

Se puede defender que **la API aplica Clean Architecture, que el móvil separa presentación, dominio y datos, y que el backend usa DDD para estructurar contextos y expresar invariantes**. Hay dependencias hacia adentro, puertos, adaptadores, composición en el borde, contextos identificables y reglas de dominio probadas. La web mantiene cero importaciones directas de presentación hacia adaptadores compartidos y cero dependencias de infraestructura hacia presentación; la prueba verifica estas reglas en todas las funcionalidades.

“100 % Clean Architecture y DDD” no es un criterio formal con una lista universal de requisitos. La afirmación técnica defendible describe el alcance y evidencia concreta, y no exige que cada consulta tenga un agregado rico. La integración con el SIE oficial, la operación de producción y la aceptación institucional se validan aparte; una arquitectura limpia no demuestra por sí sola que esas integraciones estén habilitadas ni que los requisitos funcionales hayan sido aceptados.
